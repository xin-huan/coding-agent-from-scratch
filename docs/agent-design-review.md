# Coding Agent 设计复盘与答辩笔记

这份文档用于复习本项目的设计思路、问题演进、解决措施和答辩要点。重点不是记住每一行代码，而是理解：这个 Agent 为什么这样运转，每个机制解决了什么问题，以及这些设计有什么代价。

## 一句话介绍

这是一个从零实现的本地 Coding Agent 系统。它通过 LLM 工具调用驱动本地文件读写、补丁修改和受限命令执行，并在此基础上加入 Extension 插口、上下文打包、项目记忆、任务单、三类 SubAgent、树状 Session、实时聊天界面、轻量 skill 选择和交付验证机制，目标是让 Agent 能在同一个项目里连续完成多轮开发任务，并且让用户能理解、追踪和复盘 Agent 的决策过程。

## 核心运行流程

用户输入任务后，Agent 会先构造一组消息：

1. 全局系统规则：安全边界、工具使用、测试要求、最终回答格式。
2. Extension 注入内容：项目记忆、skill 指令或其他扩展上下文。
3. 会话上下文：同一会话里最近完成的任务摘要。
4. 自动选择的 skill：例如 `diagnose`、`verification`、`desktop-python`、`web-ui`，由 skill extension 注入。
5. 用户当前任务。
6. 运行时任务状态：当前阶段、改过哪些文件、是否已测试、最近错误等。

模型不会直接操作系统，而是调用受控工具，例如 `read_file`、`apply_patch`、`run_command`。每次工具结果会写回消息历史，Agent 再根据结果决定下一步，直到满足交付条件或需要用户补充信息。

运行过程中 Agent 还会维护一份轻量任务单。对于从零创建项目，任务单来自经过 review 的 `plan_task`；对于普通修改或分析任务，系统会生成默认的“检查、修改/诊断、验证、整理结果”任务单。任务单会同时出现在实时 `[任务]` 事件和 `<task_state>` 中，作用是让模型和用户都知道当前任务推进到哪一步。

如果任务在聊天界面中运行，外层还有一层 Conversation 管理：项目和对话负责组织工作区，树状 Session 负责决定当前分支，当前分支的消息会作为用户可见历史保存；Agent 自己执行时仍以当前任务、项目记忆、当前工作区事实和运行时状态为主，不盲信旧聊天。

## 当前工具能力

项目内 Agent 的核心工具是固定的 6 个：

- `list_files`：列出工作区文件。
- `read_file`：按行号读取 UTF-8 文本文件。
- `search_text`：在项目文件中搜索文本。
- `write_file`：创建或完整替换文件。
- `apply_patch`：用精确文本块做局部替换。
- `run_command`：运行受限命令，主要允许 Python 测试、pytest 和只读 git 命令。

这套工具故意比较保守。好处是安全、可审计、行为边界清楚；代价是 Agent 不能随意安装依赖、不能任意 shell 操作，复杂项目的自动化能力暂时有限。

在核心 6 个工具之外，Extension 可以按需注册扩展工具：

- `read_context_output`：由 `ContextPackExtension` 提供，用来读取被外置的大工具输出。
- `delegate_subagent`：由 `SubAgentExtension` 在复杂任务中提供，用来委派 Researcher、Tester 或 Reviewer。

这说明工具系统不是写死在主循环里的。主循环只负责统一校验“模型只能调用本轮可用工具”，具体某个工具是否出现、由谁实现，可以交给 Extension 决定。

## 为什么删除单任务上下文管理器

我们实验过 V1/V2/V3 的单任务上下文压缩方案，但效果不好。问题主要是：

- 压缩可能丢失关键细节，导致 Agent 后续判断不稳定。
- 单个任务内部强行管理上下文，会引入额外复杂度。
- 对当前任务来说，更重要的是让 Agent 看清工作区、工具结果和测试反馈，而不是过早压缩。

所以最终策略是：彻底删除原来的单任务 ContextManager，不再保留 V2/V3 实验入口，也不再让 `read_file` 返回“缓存命中”这类语义不完整的工具结果。当前系统更依赖项目记忆、会话摘要、实时任务状态和 Extension 插口来维持连续性。

## Extension 插口架构

我们参考 Pi 框架的 Extension 思想，把 Agent 核心改成可插拔结构。Extension 可以理解为框架预留的“插口”：当运行流程走到关键节点时，外部模块可以接入自己的逻辑，而不需要直接修改 Agent 主循环。

当前暴露的主要生命周期点：

- `on_session_start`：任务开始时初始化状态或记录日志。
- `inject_context`：在用户任务前注入项目记忆、skill 指令等上下文。
- `tool_definitions`：注册扩展自己的工具。
- `before_llm_call` / `after_llm_call`：观察或调整模型调用。
- `on_context_compact`：订阅上下文打包或压缩事件，用于记录和 UI 展示。
- `before_tool_call`：修改或拦截工具调用。
- `execute_tool`：由扩展实现自己的工具。
- `after_tool_call`：观察或改写工具结果。
- `on_session_end`：任务结束后保存记忆或清理状态。

项目记忆、skill registry、SubAgent 和 Context Pack 已经从 Agent 核心逻辑中移出，变成普通扩展：`ProjectMemoryExtension`、`SkillSelectionExtension`、`SubAgentExtension` 和 `ContextPackExtension`。这样后续要加日志、权限审计、命令策略、浏览器工具、用户自定义 skill 等能力，可以通过扩展接入，而不是继续膨胀核心 Agent。

这个设计的辩护点是：Agent 主循环只保留“模型请求、工具执行、状态推进、检查点”这些核心职责；容易变化的能力通过 Extension 接入。代价是扩展 API 需要保持稳定，且扩展之间可能有顺序和冲突问题，所以目前用确定的注册顺序和测试来约束行为。

## Context Pack 上下文机制

新的上下文机制不是恢复 V2/V3，而是做成 `ContextPackExtension`。它的边界很重要：上下文治理是一个 Extension，不是 Agent 主循环里的特殊模式；模型看到的是经过打包的请求副本，原始长输出会保存到本地外置存储中，必要时再按 id 取回。

当前采用五层思路：

- 完整日志层：trace、checkpoint、聊天历史和外置输出索引保存真实运行证据，用于追溯、恢复和重新摘要。
- 大输出外置层：超过阈值的工具输出写入 `.coding-agent/context-outputs/`，模型上下文只接收摘要、关键片段和 `output_id`。
- 当前工作集层：最近几轮工具交互完整保留，尤其是刚返回的测试失败、文件内容和修改结果。
- 旧回合结构化摘要层：更早的 assistant 工具调用和对应 tool 结果会成对替换为 `<compacted_history>`，摘要按“检查了什么、改了什么、运行了什么、发现什么、风险、下一步”组织，避免留下非法的孤立 tool message。
- 跨对话项目记忆层：长期保存项目结构、用户决定、启动命令和历史任务摘要。

大输出外置层还注册了一个扩展工具：`read_context_output`。当模型看到某个长输出被替换成摘要时，可以复制真实的 `output_id`，再加 `start_line` / `end_line` 重新读取原文片段。没有看到明确 `output_id` 时不能编造 id，而应该重新运行原工具或检查当前文件。这样既不会把几万字符的测试日志反复塞进上下文，也不会让 Agent 在需要细节时只能猜。

这和旧 ContextManager 的关键区别是：旧方案试图在单任务内部主动管理和提炼工具历史，甚至让 `read_file` 返回“缓存命中”这类占位结果，结果影响了模型对真实文件内容的判断。新方案不改变普通工具的调用方式，而是在工具返回后由 Extension 判断是否外置长输出，并在模型请求过长时把旧证据打包成结构化摘要。换句话说，它优化的是“请求组装和证据取回”，不是用缓存替代事实来源。

## SubAgent 机制

SubAgent 不是默认多开模型，而是复杂任务下的一种自主决策工具。系统会先用确定性规则判断任务和工作区是否足够复杂，例如：

- 用户明确要求 SubAgent 或多代理。
- 任务包含大型、复杂、多模块、架构、性能、安全、运行失败等信号。
- 工作区文件数量较多，或者同时出现 frontend/backend/database/tests 等多个领域。

只有满足这些条件时，`SubAgentExtension` 才会向主 Agent 暴露 `delegate_subagent` 工具，并注入 `<subagent_policy>`。系统没有开放任意角色，而是固定为三个边界清楚的 SubAgent：

- `researcher`：用于大型项目调查。它只使用 `list_files`、`read_file`、`search_text`，回答“功能在哪里实现、相关模块有哪些、现有模式和架构约束是什么、风险点在哪里”。
- `tester`：用于验证策略和失败日志分析。它可以读文件、搜索和运行受限 `run_command`，负责设计测试方案、指出缺失覆盖、解释失败日志，但不能落盘补测试。
- `reviewer`：用于复杂改动后的审查。它可以读文件、搜索和运行受限 `run_command`，负责检查 patch 正确性、证据、残余风险和下一步验证建议。

三个 SubAgent 都拥有独立 context window，但都不能写文件、不能调用 `apply_patch`、不能递归创建更多 SubAgent、不能做最终决策。它们必须返回结构化 `SubagentResult`，包括 `summary`、`findings`、`artifacts`、`confidence`、`risks` 和 `recommendedNextStep`。子 Agent 完成后只把 `<subagent_report>` 摘要交回主 Agent。主 Agent 仍负责判断是否采纳、继续修复、运行最终验证和回答用户。

为了避免 SubAgent 只是 prompt 装饰，系统还加入了一个确定性的 review gate：复杂任务中一旦主 Agent 修改了文件，如果它在 Reviewer 审查完成前尝试运行最终验证，框架会把这次验证请求自动转换成 Reviewer 委派。Reviewer 审查后，下一轮 `run_command` 才会真正执行。这样能确保“复杂改动先被独立上下文审查，再由主 Agent 验证交付”是框架规则，而不是模型心情好时才遵守。

这个设计的辩护点是：SubAgent 解决的是“复杂项目多领域信息会挤爆主上下文”和“主 Agent 自己写完自己审容易漏”的问题，不是为了展示并发能力。Researcher 降低一开始乱摸代码的概率，Tester 把验证和日志解释隔离出去，Reviewer 则卡住复杂改动后的最终交付质量。系统暂时不加入 Planner 和 Implementer，因为 Planner 容易和主 Agent 的任务单职责重叠，Implementer 涉及候选 patch 合并和权限控制，风险更高；当前三个角色已经覆盖理解、验证、审查三条主链路。

## 跨对话项目记忆

我们新增了项目记忆机制，用来解决“换一个对话之后 Agent 不知道这个项目之前发生过什么”的问题。

保存内容包括：

- 项目结构快照。
- 用户做过的重要决定。
- 已知启动命令。
- 历史任务摘要。
- 最近修改文件和验证命令。

设计上它不是让 Agent 盲信记忆，而是把记忆作为方向感。真正回答或修改前，Agent 仍然要读取当前工作区文件。这样可以避免记忆过期造成幻觉。

## 聊天界面

我们实现了一个最小本地聊天界面：

- 左侧展示项目和对话。
- 右侧展示聊天消息和工具执行过程。
- 支持新建项目、新建对话。
- 支持项目/对话重命名。
- 支持对话置顶和删除。
- 保存基本会话历史。

后来发现“项目和对话关系”不能只是一个项目下拉框加对话列表，所以改成了项目树：项目像文件夹，对话缩进挂在项目下面。这更符合用户对多项目、多会话管理的直觉。

## 树状 Session

普通聊天历史是一条线：`A -> B -> C -> D -> E`。但开发任务经常需要回到某个中间节点重新尝试，例如从 `C` 之后放弃方案 A，尝试方案 B。如果仍然用线性数组覆盖历史，就会丢掉原来的 `D -> E`。

当前聊天存储把每条消息都变成树节点：

- `id`：消息自己的稳定标识。
- `parent_id`：它接在哪个历史节点后面。
- `current_message_id`：当前对话正在查看和继续的节点。

状态接口同时返回两份视图：

- `messages`：从根节点到 `current_message_id` 的当前分支，用于右侧正常聊天渲染。
- `message_tree`：完整节点树，用于左侧 Session 树目录，保留所有历史分支。

用户左键点击历史节点时只是定位查看：如果该回合属于当前可见分支，右侧聊天区会滚动到用户问题顶部；如果它属于其他历史分支，当前分支不会被切走。用户右键节点时才显示浮层动作菜单，包括“从此继续”和“恢复快照”。只有用户明确选择“从此继续”时，前端才调用 checkout 接口，把 `current_message_id` 切到那个回合对应的 Agent 回复节点；之后再发送新消息，新消息的 `parent_id` 才会接在该节点后面，自然形成新分支，而不是覆盖旧分支。为了避免旧分支污染 Agent 的内部短期上下文，checkout 时会清掉该对话缓存的 Agent 实例；下一次执行会重新创建 Agent，并继续依赖项目记忆和当前工作区事实。

这个设计的辩护点是：树状 Session 解决的是“探索失败后保留证据和备选方案”的问题，特别适合 Coding Agent 的试错场景。代价是 UI 和上下文管理更复杂，所以当前 MVP 先实现持久化树、完整回合目录、显式 checkout 和快照恢复，不急着做复杂的可视化 diff 或多分支自动合并。

树状 Session 的可视化采用“数据是树，默认视图是完整回合目录”的方案。也就是说，左侧 Session 树默认展示所有用户请求节点，方便用户像看历史目录一样浏览；当前分支内的节点和当前节点用颜色区分。普通线性后续保持同一条竖线，只有同一个 Agent 回复后面接了多个用户请求时，这些真正的分支节点才向右缩进并标记分叉数量。这样既保留树结构的可追溯能力，也避免用户为了查看旧历史而必须沿着一个个分支入口跳转。

UI 上的 Session 树节点不是单条 `ChatMessage`，而是一轮 Turn：用户请求加 Agent 回复。树上只显示用户输入的请求，左键点击该请求只定位到用户问题顶部，不在树里展开详情；右键选择“从此继续”时才实际 checkout 到对应的 Agent 回复节点，如果回复还不存在，则 checkout 到用户请求节点。这样符合用户心智：选择“给我介绍项目”这一轮之后继续输入，含义就是“基于 Agent 已经给出的项目介绍继续问”，而不是从用户消息和 Agent 消息之间的半截状态继续。

这次还修复了一个前端乐观渲染问题。发送消息时，前端会先把用户消息和“正在思考”画出来，再向后端提交请求。之前代码在乐观渲染之后才读取 `current_message_id`，导致请求携带了 `pending-user-...` 这种只存在于浏览器里的临时 id，后端报 `Message not found`。现在提交前先捕获真实父节点 id，再做乐观渲染，因此回退到历史节点后继续提问不会把临时 id 发给后端。

这里有一个非常重要的边界：普通点击树节点只切换“聊天分支”，不会自动修改磁盘文件。如果方案 A 已经修改了磁盘文件，用户点击回到方案 A 之前的聊天节点，右侧对话会回到当时的上下文，但工作区文件仍然是当前磁盘状态。Agent 后续仍会读取真实文件，而不是假装文件也自动回滚。

为了支持轻量 Workspace Tree，系统给“用户请求 + Agent 回复”这一轮绑定文件快照。Agent 运行前后会扫描工作区里的小型 UTF-8 文本文件，跳过 `.git`、`.venv`、`.coding-agent`、`.env`、二进制和超大文件；如果发现文件内容变化、新增或删除，就把这一轮完成后的相关文件状态保存到 `.coding-agent/workspace-snapshots/`，并把生成的 `workspace_snapshot_id` 挂到对应的 Agent 回复消息上。

恢复代码状态必须是显式操作：用户在 Session 树上右键某个有快照的回合节点，前端提示确认“是否恢复到该轮 Agent 运行完毕时”。后端恢复前会先把当前相关文件状态保存成备份快照，然后再覆盖、创建或删除快照中涉及的文件。这样保留了代码回退能力，但不会因为普通浏览历史节点就误改工作区。

更完整的 Coding Agent 分支系统应该把 Session 节点和代码状态绑定起来，例如：

```text
SessionNode
  id
  parent_id
  message
  workspace_snapshot_id / git_commit / branch / worktree
```

这样才能做到“极简桌面版”“带统计版”“带托盘提醒版”分别拥有自己的代码状态。当前版本已经实现了文件快照式 Workspace Tree MVP，适合小型文本项目和显式回退；下一步如果要做更强隔离，可以升级为 Git commit、临时 branch 或 worktree。

## 实时执行过程

一开始的问题是：前端等待后端完整返回后才显示消息。如果 Agent 执行时间长，界面就像没反应。

解决措施：

- 用户点击发送后，前端立即插入用户消息和“正在思考”占位。
- 后端先持久化用户消息，再启动后台线程执行 Agent。
- Agent 的 `on_event` 会实时记录状态、工具调用、Token 信息等事件。
- 前端轮询 `/api/state`，把运行中的事件展示出来。
- 任务完成后，把占位替换成最终 assistant 消息。

这个设计没有直接做 WebSocket 或 SSE，是因为当前目标是最小可用界面。轮询实现简单、稳定、容易测试。以后如果执行过程更频繁，可以再升级为 SSE。

## 执行过程折叠

用户指出：运行过程中的 `[状态]`、`[工具]`、`[Token]` 在最终回复后不应该一直铺开，否则可读性很差。

解决措施：

- 任务运行中：事件展开显示，让用户实时掌控动态。
- 任务完成后：事件默认折叠为“执行过程 N 条”。
- 用户需要复盘时，可以手动展开。

这个设计兼顾了实时透明度和最终阅读体验。

## Markdown 渲染问题

项目介绍类回答里会出现 `##`、`**`、代码块等 Markdown。如果前端当纯文本显示，用户看到的是裸语法，可读性很差。

解决措施：

- 对 assistant 消息加入轻量 Markdown 渲染。
- 支持标题、列表、粗体、行内代码和代码块。
- 用户输入仍按纯文本安全显示，避免 HTML 注入。

这里没有引入大型 Markdown 库，是为了保持项目轻量、减少依赖。代价是 Markdown 支持范围有限，但已覆盖当前最常见的 Agent 回复格式。

## 日期目录

聊天变长后，用户需要快速跳转到某一天的内容。我们为对话窗口左侧增加日期目录：

- 根据当前对话消息的 `created_at` 生成日期列表。
- 消息区按日期插入分隔线。
- 点击日期目录可以滚动到对应日期。
- 移动端隐藏日期目录，避免挤占空间。

这个设计解决的是长会话回看问题，不改变底层数据结构，只利用已有消息时间戳。

## Skill Registry

我们发现好的 Agent 不能只靠一个越来越长的 prompt。于是新增了轻量 skill 机制。

skill 是 Markdown 文件，包含：

- `name`
- `description`
- `triggers`
- `instructions`

每轮任务开始时，`SkillSelectionExtension` 会调用 `SkillRegistry`，根据用户输入的触发词确定性选择最多两个 skill，并把它们注入为任务专用 system message，同时写入 trace 和实时事件。

当前内置 skill：

- `diagnose`：遇到报错、失败、异常、性能问题时，先复现再修。
- `verification`：交付前核对需求、补测试、运行真实验证。
- `desktop-python`：桌面 Python 应用需要拆分核心逻辑和 UI 回调，并覆盖启动/回调烟测。
- `web-ui`：前端任务要关注即时反馈、进度状态、错误状态和渲染路径。
- `project-summary`：介绍项目时用记忆做方向，但必须检查当前文件。

这个设计的价值是把“工作方法”模块化。以后新增 TDD、重构、安全审查、性能分析等能力，不需要继续塞进全局系统提示。

## Diagnose 思想如何落地

我们遇到过一个典型问题：Agent 生成番茄钟后说测试通过，但用户运行 `python main.py` 后 Tkinter 回调报 `NameError: TimerState is not defined`。

根因是：

- Agent 只测试了核心计时器和设置逻辑。
- 没有覆盖 UI 回调 `_tick_once()`。
- `py_compile` 可以检查语法和顶层导入，但不能覆盖运行时回调路径。

解决措施：

- 修复 `ui.py` 缺失的 `TimerState` 导入。
- 给目标项目补 UI 回调测试，用 fake root/button/var/timer 直接调用 `_tick_once()`。
- 在 Agent 规则和 `desktop-python` skill 中明确要求 GUI 项目做启动/import smoke check，并尽量覆盖真实 UI callback。

这个案例说明：测试通过不等于需求完成，测试必须覆盖用户真实会触发的路径。

## 交付验证机制

为了避免 Agent 没测试就交付，系统里加入了运行态任务状态：

- 文件改动后标记 `changes_pending_verification`。
- Python 实现变更后标记 `implementation_changes_pending`。
- 只有完整相关测试在最后一次改动后通过，才允许进入最终回答。
- 如果测试失败，进入 `repair` 阶段，要求先诊断失败原因。
- 如果测试命令退出 0 但没有真正运行测试，也不算验证通过。

这是一种硬约束，比单纯 prompt 要可靠。它把“交付前必须验证”变成状态机规则。

## 答辩时可以这样介绍设计方案

我的 Agent 设计分为六层。

第一层是受控工具层。模型不能直接操作系统，只能调用受限工具读文件、写文件、打补丁、运行测试和只读 git 命令。这保证了安全性和可审计性。

第二层是任务状态机。系统会记录当前任务是否修改了文件、是否完成验证、最近一次命令是否失败。这样可以用程序规则约束 Agent，不让它在未测试时直接宣称完成。

第三层是 Extension 插口。项目记忆、skill、Context Pack 和 SubAgent 都不是硬塞在主循环里，而是通过生命周期 hook 接入。这样主循环保持稳定，能力可以渐进扩展。

第四层是上下文和记忆层。Context Pack 处理长工具输出和旧回合压缩，项目记忆保存跨对话的结构、用户决定、启动命令和历史摘要。它们提供方向感，但不替代读取当前文件。

第五层是 SubAgent 协作层。复杂任务中主 Agent 可以委派 Researcher、Tester、Reviewer，各自拥有独立上下文和受限工具。子 Agent 负责调查、验证或审查，主 Agent 负责合并证据和最终裁决。

第六层是聊天产品层。界面不是只显示最终结果，而是实时显示 Agent 的工具执行过程，完成后折叠；同时支持项目树、对话管理、日期目录和树状 Session，让用户能追踪、回退和复盘多轮开发过程。

## 常见评委问题与回答

### 为什么不完全依赖 prompt？

因为 prompt 只能指导模型，不能保证模型一定遵守。这个项目把关键要求做成了机制：工具受限、状态机阻止未验证交付、skill registry 确定性选择工作流程、trace 记录行为。这些都比单纯提醒模型更可靠。

### 为什么工具要受限？

Coding Agent 有本地文件写入和命令执行能力，如果给任意 shell 权限，风险很高。受限工具虽然牺牲了一些灵活性，但换来了安全边界、可测试性和可解释性。后续可以逐步扩展工具，而不是一开始放开所有权限。

### 为什么项目记忆不能直接替代读文件？

记忆可能过期。用户可能手动修改项目，或者上一次任务没有完整记录。因此项目记忆只提供方向，真正回答和修改前仍要检查当前工作区。这能降低幻觉和错误决策。

### 为什么选择轮询而不是 WebSocket？

当前阶段目标是最小可用聊天界面。轮询足够实现实时感，代码简单，测试容易，也不增加协议复杂度。如果后续事件频率变高，或者需要更低延迟，可以升级为 SSE 或 WebSocket。

### 为什么 skill 选择是触发词，而不是再问一次模型？

触发词选择确定、便宜、可测试。它适合当前阶段的内置 skill。用模型选择 skill 更灵活，但会引入额外不确定性和成本。未来可以做混合方案：确定性规则先筛选，再由模型在候选 skill 中选择。

### 为什么 SubAgent 不是所有任务都启用？

因为 SubAgent 有额外模型调用成本，也会增加汇总复杂度。小任务通常主 Agent 自己读两三个文件就能完成，强行拆分只会变慢。当前系统先用任务关键词、项目规模和领域数量判断是否值得暴露委派工具；即使启用，也只开放 Researcher、Tester、Reviewer 三个受限角色。复杂任务发生文件改动后，review gate 会拦截过早的最终验证请求，要求先审查再验证。这体现的是“按复杂度启用能力”，不是堆功能。

### 为什么只加 Researcher、Tester、Reviewer，不加 Implementer？

因为这三个角色的价值明确，风险也可控。Researcher 解决“先理解项目”，Tester 解决“怎么验证和解释失败”，Reviewer 解决“改完以后独立审查”。它们都不落盘修改，所以权限边界清楚。Implementer 一旦加入，就涉及候选 patch、冲突合并、谁有最终修改权、如何避免多个 Agent 同时写坏文件等问题，控制层复杂度会明显上升。当前阶段先不加，是为了让系统稳，而不是为了显得功能多。

### 树状 Session 为什么不直接回滚代码？

因为聊天历史和工作区文件是两个不同状态。普通点击历史节点不会自动修改磁盘文件，这样更安全，不会因为用户点错一个聊天节点就把代码恢复到旧状态。需要恢复代码时，用户必须右键有快照的回合节点并确认；系统恢复前会先备份当前相关文件。Agent 继续工作时仍会读取当前真实文件，避免基于过期假象做判断。

### 什么时候需要 Workspace Tree？

当用户真的需要“方案 A 和方案 B 各有一份代码”时，就需要 Workspace Tree。当前实现是简单版：每个有文件变更的 Turn 节点绑定 `workspace_snapshot_id`，右键可以恢复该轮完成后的相关文件状态。它的优点是实现成本低、适合演示和小型项目；不足是只覆盖文本文件和变更文件，不提供完整 Git 分支隔离。更强版本可以继续升级为 Git commit、Git branch 或 Git worktree。

### 树状 Session 对上下文管理有什么帮助？

它让当前对话上下文只沿着一条分支展开。用户从历史节点重新尝试时，右侧只显示新分支路径，不会把旧分支的失败尝试全部塞进当前可见上下文。对模型来说，这能减少无关历史干扰；对用户来说，旧分支仍然保留，方便比较不同方案和复盘。

### 如何证明 Agent 不是“看起来会做”，而是真的会做？

通过测试和状态约束。比如文件改动后必须重新运行相关测试，测试失败会进入 repair 阶段；GUI 项目要求覆盖 UI 回调；聊天界面行为也有单元测试覆盖。最终交付时报告真实命令结果，而不是口头承诺。

### 这个系统目前最大的不足是什么？

当前工具和 skill 机制还比较轻量。SubAgent 已经有 Researcher、Tester、Reviewer 三个角色，但还不是并行任务调度系统，主 Agent 仍是顺序委派、汇总和裁决。工具层缺少更丰富的项目分析能力，例如依赖安装策略、浏览器自动化、结构化 AST 编辑等。skill 选择也只是触发词匹配，还没有版本管理、优先级配置和用户自定义目录。上下文摘要目前是规则化摘要，不是 LLM 语义重写，所以它稳定、便宜、可测试，但对复杂跨文件因果关系的概括还可以继续增强。

## 后续优化方向

- 增加用户自定义 skill 目录。
- 为 skill 增加优先级、互斥规则和适用项目类型。
- 将实时输出从轮询升级为 SSE。
- 给聊天 UI 增加搜索、按任务状态筛选、历史摘要面板。
- 把文件快照式 Workspace Tree 升级为 Git commit、branch 或 worktree 隔离。
- 给树状 Session 增加分支命名、分支对比和从某个节点创建代码工作区副本。
- 增加更强的验收机制，例如自动运行入口 smoke test、浏览器 UI 测试、覆盖率摘要。
- 给工具层增加结构化代码编辑能力，减少大段文本替换的脆弱性。
- 为长期项目记忆增加压缩和冲突检测，避免记忆越来越长或过期。
- 给 Context Pack 增加更强的语义摘要器，在保留可测试规则的同时总结“为什么这样改”。
- 支持多个 SubAgent 报告汇总为一个任务诊断报告，但默认仍只保留 Researcher、Tester、Reviewer 三个角色。
